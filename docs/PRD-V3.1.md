## 2. 修复 BMI 24 临界点热量跳变

已定位旧 nutrition.ts 中减脂判断包含 `bmi >= 24`，当 BMI 低于 24 时直接将缺口归零。原 docs/NUTRITION.md 和 tests/core.test.ts 也体现了这项旧保守策略，属于政策及交互设计需要升级，而不是基础代谢公式写错。

复现档案：男性、25岁、173cm、久坐、目标60kg、缓慢减脂（标准缺口300千卡），假设没有其他安全限制或趋势修正：

| 指标 | 72kg | 71kg |
|---|---:|---:|
| BMI | 24.06 | 23.72 |
| 静息能耗估算（BMR） | 1681.25 | 1671.25 |
| 总消耗估算（TDEE） | 2017.5 | 2005.5 |
| 旧算法缺口 | 300 | 0 |
| 旧算法每日目标（整数） | 1718 | 2006 |

不得继续以 BMI 24 作为一刀切的缺口开关。也不得简单改成 BMI 大于18.5就一律维持完整缺口。采用下一节的连续衰减方案，并区分用户意愿、系统建议、实际允许缺口和安全停止原因。

## 3. BMI 百分比连续衰减算法（本次核心）

中国成人 BMI 正常范围为18.5至不足24。18.5是绝对低体重防护边界，不是推荐目标；接近低体重时可以根据风险提前停止减脂。正常 BMI 默认维持，明确主动选择减脂且健康适用评估通过的成年人可以使用温和缺口；不得仅以 BMI 正常或目标 BMI 合法认定个人适宜减重。对于年龄、疾病、药物、异常体重趋势或其他需专业评估的情况，执行保守保护规则。

BMI 越接近24，缺口保留比例越高；越接近18.5，比例越低。BMI≥24时系数1，BMI≤18.5时系数0，中间线性变化。百分比表示标准缺口的保留比例，不是每日总消耗的百分比。

参考实现（计算单位统一为 kg、cm、kcal/day，伪代码，按实际类型调整）：

```ts
const bmi = calculationWeight / (heightCm / 100) ** 2;
const bmiFactor = Math.max(0, Math.min(1, (bmi - 18.5) / 5.5));
const standardDeficit = Math.min(requestedDeficit, tdee * 0.15);
const distanceCap = Math.max(0, (calculationWeight - targetWeight) * 300);
const scaledDeficit = Math.min(standardDeficit, distanceCap) * bmiFactor;
// 由已有健康筛查及经复核的安全规则确定，不可绕过。
const effectiveDeficit = eligible && goal === '减脂' && !targetReached
  ? Math.max(0, Math.min(scaledDeficit, safetyCap, Math.max(0, tdee - energyFloor)))
  : 0;
const dailyKcal = Math.round(tdee - effectiveDeficit);
```

以上公式为产品工程建议，并非医学指南规定的公式，未经临床验证。现有15%限制、距目标体重系数300、男女最低能量保护等同样属于应用保守策略，应核对可靠成人指南及其适用性，记录依据，不能宣传为临床处方。safetyCap 必须明确实现趋势、健康、年龄、营养及其他安全限制，不能使用未定义值或用无穷大默认绕过保护；如输入或健康筛查不适用，按原有拦截或专业评估流程处理，而不是直接生成食谱。最低能量边界无法满足时拦截；不允许四舍五入造成实际目标低于保护下限或错误显示缺口。到达目标或 BMI≤18.5 不再减脂；若已经低体重，应提示评估而非继续自动生成减脂方案。对最新体重和趋势估计均检查安全边界，不得因平滑机制拖延必要保护。

示例（标准缺口300、未受其他上限影响，表中为四舍五入显示）：

| BMI | 保留比例 | 缺口 |
|---:|---:|---:|
| ≥24 | 100% | 300 kcal |
| 23 | 81.8% | 245 kcal |
| 22 | 63.6% | 191 kcal |
| 21 | 45.5% | 136 kcal |
| 20 | 27.3% | 82 kcal |
| 19 | 9.1% | 27 kcal |
| 18.5 | 0% | 0 kcal |

以第2节档案为例，在单次体重作为计算依据、主动选择减脂且通过健康筛查、无其他限制的演示条件下，72kg 时目标约1718千卡，71kg 时系数约94.96%，缺口约285千卡，目标约1721千卡，而不是突然变为2006千卡。实际采用趋势计算后结果可能不同。热量目标可以合理上升或下降，不要求单调下降；应避免无解释突变。接近目标时 distanceCap 自然衰减，达到目标时缺口归零。

## 4. 用户热量缺口选择与安全限制

在个人档案现有目标设置内提供系统推荐、维持体重（0）、缓慢减脂（标准300）、适中减脂（标准400）、自定义标准缺口（可提供100、150、200、300等快捷值）。选项的实际可用性由安全校验决定。明确标注用户选择的是“标准缺口”，并非承诺实际每天扣减这么多。保存长期偏好；体重变化不应无提示重置该偏好，但安全规则可以限制实际缺口，明确说明原因。正常 BMI 的默认推荐维持；从超重进入正常范围时，对已明确选择且仍符合条件的减脂偏好进行重新评估，不静默清除或自动强迫继续减脂。到达目标后进入维持，保留偏好作为历史或后续配置，不继续执行赤字。禁止低于正常 BMI 下限的减脂目标，保留未成年、孕哺期、进食障碍风险、特殊疾病、医嘱饮食等限制。校验自定义值为有限非负数并受安全上限约束。对旧用户缺少主动选择正常 BMI 减脂的信息，迁移为安全默认并允许核对；不伪造用户同意。

## 5. 体重趋势、热量调整与计算说明

最新有效称重用于展示当前体重。用于计算目标的体重可采用经验证的近期趋势或均值，明确展示计算体重、统计窗口、样本数、记录不足时的回退逻辑。复核旧 0～7 天、14～28 天窗口及均值变化规则；以真实日期为准，处理稀疏记录、连续波动、快速减重、突然异常。调整频率和幅度须有明确依据和测试，不以平滑为由延迟安全处理。年龄、身高、活动、目标、健康状态变化时重新评估。活动因子与运动信息避免重复计入。同步重新计算蛋白质、脂肪、碳水等目标；检查最低能量与营养可行性。

首页热量卡片增加折叠式计算依据：最新体重、计算体重、BMI、BMR、活动系数、TDEE、用户标准缺口、BMI缺口保留比例、距目标限制、安全修正、实际缺口、最终每日目标、当前模式、上次调整时间及原因。显示当前减脂意愿与实际模式的区别。只在需要时提示目标变化，避免重复提示。更新 docs/NUTRITION.md、算法版本及相关测试；替换旧测试中“正常 BMI 必然维持”的绝对断言，仍测试默认维持及不符合条件时的保护。

## 6. 首页与食谱热量目标一致性

main.tsx 的最新 targets 与 PlanPage.tsx 的 plan.targets 是不同时间口径，不能直接互相覆盖。区分当前建议目标、方案生成时目标、当日计划摄入、实际记录摄入。首页和食谱明确标注旧方案与新目标的差异，并提供更新尚未执行部分的入口。普通称重变化不应立即禁用全部换菜、调整用量，也不应通过 stale 无条件清空菜品锁定。重大健康、营养或档案变化应及时重校验，必要时限制不适用的操作。重新生成时保留已执行餐次、历史目标、采购和库存流水、用户锁定；未来部分如无法满足最新限制，提示具体冲突。不可将新热量目标写进旧历史快照冒充当时目标。

## 7. 起始体重、最新体重和减重进度

拆分起始体重、起始日期、最新实际体重、目标体重、称重流水。现有 Dashboard 以 profile.weight 同时作为起始体重，档案又称当前体重，存在修改档案后重置累计减重的风险。起点只能由明确开启新阶段或修正起点的操作改变。档案中的当前体重如允许编辑，应与最新称重来源协调，不能显示修改成功却仍使用旧称重数据；选择明确的单一更新路径。累计减重=起始体重-当前体重；距离目标按当前与目标差计算；有效减脂阶段进度=(起始-当前)/(起始-目标)，进度条仅视觉限制0～100%，真实数值保留。处理体重反弹、达到或超过目标、目标改变、维持模式、起点缺失、分母为零。旧数据迁移保留可确认的起点，不能捏造称重日期。用户主动重设阶段时明确确认，不删除历史记录。

## 8. 体重记录与日期边界

检查新增、编辑、删除最新或历史记录、同日重复记录、修改日期导致冲突、未来日期、空值、负数、非有限数、合理范围及备份导入。统一最新有效记录选择逻辑、单位、当地日历日期以及近7/30天边界（明确是否含当天）；营养趋势和首页趋势采用一致规则。处理只有一条记录、多条相同重量、图表横轴同日、修改记录后趋势变化、删除最后一条记录等。起始档案没有实际称重日期时不能伪造图表点。避免 NaN、Infinity、除零、错误轴范围；体重最新显示与目标计算的差异需解释。

## 9. 采购进度与状态统一

Dashboard.tsx 与 ShoppingPage.tsx 当前存在不同筛选和完成判定，且首页0/24项与16种待买使用不同计数单位。建立共享派生函数，按稳定采购项目ID（商品+批次等）计算完成、部分购买、待购、待核对、无需补购；另按标准采购商品ID去重计算待买种类。明确区分批次数量、采购项目数、商品种类、库存覆盖种类。同一种商品跨两批可算两项但只算一种。首页、批次、全周汇总使用同一逻辑；不把批次项目与去重商品直接相除。无需求显示无需采购，不显示0/0。库存覆盖不等于实际购买；清空后可能新增补购需求，但历史购买仍保留。区分计划进度与历史实际购买，避免分母变化造成误解。

## 10. 采购完成与价格、换算状态分离

旧 purchaseStatus 以 confirmed、remaining、estimate 混合判断。数量已经满足而单价或实际支付未知时，不应仅因金额缺失显示部分购买；缺少可靠生熟、毛净、体积或包装换算时，应单独标为数量待核对。通过明确的业务字段区分数量覆盖、购买事实、价格完整性、换算完整性。测试全购、部分购、未购、库存覆盖、价格未知、实付0元（确认确实免费）、实际支付未填、追加购买、修正、撤销、清空库存等。不得把历史购买勾选当成当前库存充足。

## 11. 费用及预算核对

统一已实际支付、已购未填实付的参考估算、剩余预计采购费用、预计总支出、食材消耗价值、剩余预算等口径。实际支付按交易日期归属，计划费用按明确计划期间归属；计划外采购应进入对应实际支出统计。未知金额不得按0元处理，显示已知部分及缺失状态。预计总支出按已知实际支付+已购未填金额的合理估算+尚需采购估算汇总，避免重复计算或遗漏；缺价格时明确总额不完整。对消费价值、包装余量、既有库存价值和现金支出分别统计。核对批次、分类、全周汇总与预算关系；历史实付不能因库存清空、食谱删除、参考单价变动而消失。明确区分旧交易价格和当前重估价格。检查提前购买、跨周结转、计划外购买、同日多笔交易、撤销与修正。

## 12. 库存账本与长期数据一致性

所有页面读取同一真实库存账本及统一商品ID。确认购买按实际数量入库；实际取用扣除；生成食谱仅形成计划需求；完成用餐不重复扣除已取用量。验证同日多次购买累计、交易修正、撤销购买、撤销取用、单项清空、全部清空、撤销清空、刷新、跨周、重新生成、补购、导出恢复。清空通过流水调整，不删除购买和付款历史，不让旧数据复活；避免负库存、重复点击重复扣减、事务部分失败。撤销基于原事件且幂等，不能重复恢复。已有库存优先复用，缺口才补购。不同原材料不能因相似用途替换而互相转移库存；自制生熟状态按可靠转换统一采购，不与真实即食商品混淆。库存永久保存，不增加过期判断、自动失效或有效期管理；食品是否适合食用由用户自行确认，保留必要烹饪及储存建议。

## 13. 备餐、分装和用餐进度

首页下一批备餐旧逻辑使用 made，采购备餐页部分逻辑使用 taken。统一任务阶段派生函数，区分待取用、已取用、已制作、已分装、已完成用餐（只统计实际支持的记录）。不同阶段分别显示进度与明确名称，不将取用完成等同于备餐或用餐完成。下一批待处理任务按日期和未完成阶段确定，正确处理逾期未执行、当日任务、后续批次、无需某阶段的任务。任务身份稳定，合并工序不重复扣库存；撤销某阶段不应意外撤销其他独立阶段。历史任务保持原样。采购次数与备餐次数独立，不擅自增加采购批次。继续按厨具匹配，不重新引入烹饪时间限制。

## 14. 营养计算及数据库校验

核对 nutrition.ts、diet-check.ts、catalog.ts、planner.ts、ui.tsx 与营养数据。每100g营养值必须与食材真实状态（生、熟、干、即食）一致，重量换算不能重复应用。验证热量、三大营养素、膳食纤维、钠、钾、钙、铁、叶酸、B12及所有现有指标；营养来源可追溯，未知值不能当0。热量与宏量能量计算的差异需考虑数据库定义、纤维和舍入，不强行修改真实数据。检查每日、全周日均、覆盖率、低值、超限与未知状态。新增油类统一分类统计，复合调料依据实际成分或可靠标签计算钠及营养，不能当纯盐、纯胡椒或纯柠檬；没有可靠数据则标记缺失。低钠盐等产品与普通盐数据区分，不以“低钠”名称猜测具体钠或钾含量。替换和份量取整后重新校验营养、采购和备餐。不可根据单项营养估算诊断疾病或承诺治疗。保持健康适用筛查及过敏保护。

## 15. 计划摄入与实际摄入

食谱营养是计划量，不代表吃下的数量。完成本餐、调整实际用量、撤销完成必须区分真实记录和计划。如果现有系统仅记录任务完成而没有实际摄入量，不得新增伪造的实际热量数字；可标注已完成餐次或按计划估算，并说明局限。库存取用不等于吃下，分装、烹饪损耗、剩余、丢弃不重复统计。已执行的历史菜品、数量及事件不能被新方案覆盖。保留更正或撤销真实记录的入口及审计信息。

## 16. 多人份量、单位及包装

个人营养目标与全家采购量分离：2人用餐时每人目标不翻倍，总采购和备餐按人数计算，实际登记的购买数量不再乘人数。修改人数只影响未执行部分，历史数量不改。核对克、千克、斤、毫升、升、个、瓶、袋、盒等单位。液体体积与重量依可靠密度换算；包装数、每包装净重、毛净关系、生熟出成率分离；无可靠换算提示待核对。瓶装油、醋、酱油显示合理单位。汇总和采购、成本、库存采用相同精确值，显示层舍入不反向影响原始数据。

## 17. 多食材锁定、偏好及替换

保留自动、优先、锁定、排除四状态，互斥且多食材可同时锁定；所有入口使用最新已确认设置，禁止旧方案覆盖新偏好。锁定是本周合理使用，不是每餐使用；避免象征性极少量满足锁定。默认分类数量是优化目标，用户硬上限冲突应说明；固定水果、固定早餐、必选菜、厨具、过敏与锁定冲突不得静默忽略。换食材必须改变核心食材，换做法可保留；同类替换更新真实菜谱数据及营养、价格、采购、备餐，不转换库存身份。保留分类食谱大全及原材料大全。食材库丰富与集中采购并行，库存优先、不必要品种尽量减少。体重更新不丢失用户偏好或锁定；已执行餐次不可直接覆盖。

## 18. 日期、历史方案及版本兼容

检查今天、明天、下周一、自定义日期、跨月、跨年、当地时区及跨午夜刷新。区分方案未开始、执行中、结束；过去食谱首日不能冒充今日。已过日期和实际已执行餐次是不同状态。历史方案使用对应历史快照、目标、费用、执行记录（若旧版无记录则明确未知），不得绑定当前方案的任务状态或当前库存冒充历史。当前价格重估单独展示。版本升级保留历史原始信息；旧版计划仍可查看，若需更新未执行部分则明确提示及兼容处理。

## 19. 全站异常输入和统一计算来源

检查所有数字、金额、百分比、单位、日期、进度条、表单、营养数据。防止 NaN、Infinity、除零、负库存、负采购量、空字符串转0、未知值当0、极小非零量误判、浮点残差、重复记录、无效分母。内部精度统一，汇总从原始量计算，显示层统一格式化，不从展示舍入数反推业务。建立共享领域函数/数据选择器：有效最新体重、起始及进度、营养目标、采购数量和状态、费用、真实库存、备餐阶段、食材偏好。各页不重复维护互相矛盾的状态。避免为重构而过度抽象。

## 20. 异步、并发、数据持久化

审查 React 状态、快速连续操作、IndexedDB 事务、多个标签页、保存失败、Web Worker 返回及取消生成。使用最新数据或明确版本快照校验，避免旧生成结果覆盖新库存、档案、偏好或执行记录。生成期间若关键输入改变，应重新评估或提示重新生成；失败保留旧方案和已保存偏好。库存事件幂等且原子写入；历史和真实流水不受普通 UI 更新影响。备份恢复覆盖旧版格式、损坏输入、重复事件、迁移冲突与回滚，不能自动丢弃用户数据。维持离线能力及本机隐私；本地存储仍可能因清除站点数据、设备更换等丢失，应保留备份功能。

## 21. 自动化测试与验收清单

先复现确认问题，再添加失败测试，再修复并验证。至少覆盖：

1. 72kg→71kg 旧算法跳变复现；新算法在明确的适用及无额外限制条件下约1718→1721千卡，不强制清零。使用未舍入数验证系数与能量关系。
2. BMI 18.49、18.5、19、20、21、22、23、23.99、24、24.01，以及肥胖边界；系数连续、非负且不超过1，BMI≤18.5不允许减脂。
3. 正常 BMI 系统默认维持、主动减脂通过评估、主动维持、不符合评估、达到目标、目标接近低体重、非法目标、特殊健康条件。
4. 标准缺口0、100、150、200、300、400及自定义无效值；15%限制、距离限制、最低能量、趋势调整、安全停止及合理热量上调。
5. 单次波动、记录稀疏、快速减重、趋势窗口及不同日期；删除最新记录、编辑同日记录、未来日期、跨时区、异常体重。
6. 新目标与旧方案分离；普通称重不无条件禁用换菜或清除锁定；重大变更正确校验；已执行及历史记录保留。
7. 起始体重不因档案更新被重置；体重反弹、达到目标、维持模式、分母为零正确显示。
8. 首页与采购页同一统计；跨批次同商品计数；全库存覆盖；零需求、部分购买、价格未知、换算未知。
9. 实际支付、估算、剩余费用、预算、分类汇总、计划外及跨周采购一致。
10. 入库、取用、完成用餐、撤销、单项及全部清空、撤销清空、同日多次购买、刷新及跨周不重复或复活库存。
11. 备餐取用与制作等阶段独立；任务进度及下一批正确；已执行食谱不被覆盖。
12. 个人营养和多人采购倍数；单位、包装、生熟及毛净换算；调整实际数量、食材替换后全链路一致。
13. 营养缺失、复合调味料、食用油分类、每日及周均营养口径；计划与实际摄入区分。
14. 多食材锁定、固定搭配、严格食材池、同类替换及库存优先；已有功能不回退。
15. 至少100个随机种子覆盖多档案、厨具、库存、餐次、正常/超重等适用条件；报告成功率、失败原因、实际运行数量与耗时，不以降低营养或安全要求提高成功率。
16. 快速点击、保存失败、Worker取消、并发标签页、旧数据迁移、备份恢复、离线使用及 PWA 更新。
17. 真浏览器检查首页、食谱、采购、备餐、库存、生成设置、历史方案等关键流程；至少360px、390px、430px，保留 V3.0 UI。
