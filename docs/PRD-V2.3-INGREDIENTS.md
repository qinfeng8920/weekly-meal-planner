# 天天减 V2.3：全品类采购精简与智能食材替换专项

项目仓库：https://github.com/qinfeng8920/weekly-meal-planner

正式网站：https://qinfeng8920.github.io/weekly-meal-planner/

## 1. 本次目标与范围

在最新代码基础上升级全品类采购优化，而不仅仅是调味料。用户希望每周集中采购少量种类、大份分装，并使用家中已有食材完成合理的一周食谱。不要为每道菜单独采购用途相近的食材，也不要为了凑菜谱多样性增加不必要的商品。

核心原则：相同商品统一采购；不同商品按用途合理替换；先选择本周实际使用的原材料，再生成和优化食谱；已有库存优先，缺多少才采购；兼顾营养、口味、成本、制作可行性与长期多样性。

本文件是 V2.3 的专项补充，不要求重新开发已有功能。先检查当前代码和未完成的 V2.3 任务，合并实施，不覆盖已修复的问题。不要新增主导航、付费 AI API 或大规模改版。

实际案例：目前部分菜谱需要菜籽油、部分需要橄榄油，凉拌菜还指定苹果醋。对于只有蒸锅和煮锅、主要蒸煮凉拌的用户，如果已有适用橄榄油和米醋，许多菜可直接使用它们，不必额外采购其他同用途商品。本次要求将这一原则扩展到所有采购分类。

## 2. 明确三个不同的数据概念

1. 营养食材 ID：区分生熟状态、品种、部位、营养组成，用于准确计算菜谱营养。
2. 采购商品 ID：表示实际需要购买的原材料或真实即食商品，用于采购、价格、库存和分装。自行制作的熟鸡胸肉与生鸡胸肉映射至同一采购原料，使用可靠的烹饪出成率转换；明确购买即食熟鸡胸肉时才独立采购。
3. 功能替换关系：表示不同商品在特定菜谱、餐次、烹饪方式下可互相替代，例如橄榄油替代菜籽油。不同商品仍然保持独立采购 ID、库存、价格和购买历史。替换是修改实际菜谱，不是把不同商品库存合并。

禁止用字符串相似度、同一大类、相同热量或简单去掉“生/熟”字样直接推断所有商品等价。禁止仅在 UI 层隐藏食材或合并采购项目而不修改底层食谱。

## 3. 建立全品类替换知识库

检查 foods.json、catalog.ts、food-semantics.ts、purchase-food.ts、purchase-category.ts、ingredient-pool.ts、meal-rules.ts、meal-catalog.ts、planner.ts、logistics.ts、execution.ts、inventory.ts、prices.ts 及最新实际对应文件。复用已有规则，不重复创建平行系统。

建议建立独立、可维护的 substitution 模块或结构化配置。每条规则至少记录原食材、目标食材、可替换的菜谱角色、适用餐次/菜系/烹饪方式、限制条件、数量换算方式、是否必须改做法、是否需要用户确认、过敏原/营养影响、数据来源或人工审核依据、规则版本。缺失可靠数据时禁止自动替换，提示或采用经过审核的替代菜谱。

规则分三档：
- A 直接替换：用途相同、烹饪方法兼容、数量关系明确且营养与安全复核通过，例如合适的植物油之间、适合该菜的食醋之间。不是所有同类调味料都自动等价。
- B 条件替换：需要调整份量、调味、烹饪步骤、熟化要求或配餐结构，例如鸡胸肉替换去皮鸡腿肉、杂粮米替换其他谷物、部分叶菜互换。优先选择已有真实可执行的变体菜谱；生成变体时使用经过审核的模板，不拼接不可靠的烹饪说明。
- C 重新配餐或禁止：用途、营养角色、过敏风险或工艺差异较大，不能直接替换。例如牛奶与普通豆浆不能无条件等量互换，坚果与烹调油不能直接等量替换，鱼虾与豆腐不能按克数无条件互换。可在全餐或全周重新优化并验证营养后选用其他菜谱；禁止使用过敏、忌口、不适合厨具的商品。

以下是规则设计示例，不是直接上线的无条件白名单。请对现有菜谱逐类核验并编写测试。

| 采购类别 | 优化方向 | 必须注意 |
|---|---|---|
| 肉类 | 在适合蒸煮、汤、拌菜的菜谱中复用同一批鸡胸、去皮鸡腿、适宜部位的瘦肉等 | 区分部位、带骨/去骨、脂肪及熟化要求；红肉与禽肉不能无条件等重替换 |
| 鱼虾海鲜 | 适用时复用同一类鱼肉或净虾仁，减少一餐一种海鲜 | 带壳/带骨可食率、鱼类脂肪差异、过敏原及做法；不把鱼和甲壳类视为可任意互换 |
| 鸡蛋 | 自制水煮蛋、蒸蛋、其他蛋菜统一采购鸡蛋 | 全蛋、蛋清及购买的即食蛋产品不能混淆；若自制蛋清须考虑蛋黄去向及实际采购量 |
| 豆制品 | 适合的汤、炖菜、蒸菜优先复用一种常用豆腐 | 南豆腐、北豆腐、豆干的含水量、蛋白质、钙和质地不同，需调整做法与份量 |
| 乳制品/豆浆 | 优先同一款无糖酸奶、同一款奶类或豆浆，减少不同口味包装 | 无糖/含糖、脂肪、钙、蛋白质、乳糖及过敏原不同；牛奶和豆浆不可默认营养等价 |
| 主食谷物 | 优先复用已有的糙米、杂粮米、燕麦等，按餐次选合适主食 | 干熟换算、吸水率、能量及纤维；燕麦粥、米饭、面包不是所有菜谱均可直接替换 |
| 薯类/玉米 | 红薯、土豆、玉米按营养和菜谱角色替换部分主食 | 不按等重直接视为相同热量；不把薯类主食简单计入非淀粉蔬菜 |
| 蔬菜 | 优先在深绿叶菜、十字花科、瓜类、根茎等相近用途中复用 | 保证多样性、深色蔬菜、纤维及微量营养；菠菜等不能在所有菜谱中直接替代西兰花 |
| 菌菇 | 适合汤和炖菜时复用同一款菌菇 | 干鲜重量、泡发率、口感和食品安全 |
| 水果 | 在早餐、加餐等可替换位置复用少量品种 | 不按含糖量或克数简单等价，遵守用户水果偏好，不默认禁止完整水果 |
| 坚果种子 | 适合加餐时优先一种原味无盐坚果 | 严格过敏筛查、脂肪和能量差异；不将坚果油、坚果酱与完整坚果默认等价 |
| 烹调油 | 一周优先一种适合当前厨具和烹饪方式的主油，库存优先 | 区分凉拌、加热及提香用途；香油不默认替代全部烹调油；按实际脂肪、能量、密度计算 |
| 食醋 | 适合的凉拌或调味菜优先一种已有食醋 | 关注酸度、风味、含糖调味醋，必要时调整用量 |
| 酱油/酱料 | 优先适合菜谱的常用生抽或其他已有酱料 | 钠、添加糖、过敏原、浓度和调味作用；老抽、蚝油、生抽不能无条件互换 |
| 葱姜蒜/新鲜香料 | 优先复用已有新鲜调味食材；非必要时可省略 | 按去腥、增香等实际功能判断，不能任意互相替代 |
| 干香料/其他调味品 | 优先少量常用调料，非必要装饰性配料可省略 | 不牺牲关键工艺、营养、过敏安全；非必要省略须同步改配方和做法 |
| 其他加工或包装食材 | 优先复用规格、成分和用途相容的现有商品 | 不混淆即食成品、自制熟料、干货、冷冻食材及不同包装配方 |

必须遍历当前食材库的全部采购分类，给出规则覆盖清单：已支持自动替换、仅支持条件替换、必须重新配餐、暂无可靠规则。对暂无规则的商品保守保留，不要求为了覆盖率强行设置替换关系。

## 4. 先建核心食材池，再做全周采购优化

沿用现有少量种类、均衡搭配、丰富多样三个模式，统一实现，不再新增复杂的模式。

先读取实际库存、锁定食材、忌口、过敏、厨具、餐次偏好、用餐人数、预算、采购次数和备餐周期；在符合条件的候选食材中优先确定可复用的本周采购商品及常用调味料；再选择相容的菜谱及变体，优化份量和全周安排。

对少量种类模式，单人主要食材可先以肉鱼虾2–3种、蔬菜约4种、主食2–3种、水果1–2种（允许不吃）、蛋奶豆制品3–4种、坚果1种为参考；不是硬性营养限制。主要食材约13–17种作为参考目标，常备调味料与新鲜调味食材另计。最终数量根据营养与用户实际偏好确定。均衡与丰富模式保留更宽范围，但也避免无意义的一次性采购。

优化对象是整周新增实际采购商品种类数，不是菜名数量，也不只是肉菜主食的种类。计算时使用统一采购商品 ID，并考虑已有可用库存、包装余量和真实补购需求。区分“本周使用多少种食材”与“实际需要买多少种”。用已有多种调料并不必然增加采购次数，但仍可按用户偏好简化使用。

建议采用约束搜索/候选方案评分或迭代局部优化：
- 硬约束：用户明确过敏、忌口、严格指定食材、真实厨具、合理餐次搭配、同餐去重、营养安全、用户锁定与已执行任务保护、固定采购次数、实际可执行的备餐方法。
- 优化目标：减少额外商品种类和一次性使用的食材；优先覆盖已有库存；减少采购费用和包装余量；增加共同备餐工序；维持食物多样性、口味与用户偏好。
- 在同等营养及可行性下优先选择可复用的采购组合，再在合格方案中随机化，保持不同周有变化。

禁止为了少买食材而强制吃完包装、增加热量、使用过敏食物或忽略重要营养。若目标不可行，输出具体缺失类别和最少新增商品方案，允许用户确认；不要偷偷添加明确禁止的食材，不要无限搜索。

## 5. 库存优先及常用食材偏好

沿用现有食材池选择页面与饮食偏好，默认自动优化，无需用户逐个设置替换规则。

在现有界面提供简洁的“优先使用库存”“仅使用指定食材”选项（复用已有设置），以及可折叠的常用食材/调味料偏好。允许选择默认主油、常用食醋、常用主食、蛋奶豆制品、肉类等。支持锁定喜欢的商品与排除不喜欢的商品。

有足够库存且满足菜谱用途时，优先使用；库存不足时比较继续补同一商品与使用其他已有相容商品的代价。不要为用尽库存而选用不合理搭配。严格模式只使用指定商品和用户明确允许的基础调料；无法满足时提示原因。

不同商品库存不能直接合并。例如菜籽油不能改名为橄榄油，实际使用哪一种就扣哪一种；不同鱼种、肉类部位、不同豆腐等同理。生熟原料映射与真实即食商品沿用 V2.1 规则。

库存继续按用户要求作为长期账本：购买多少记录多少，实际取用才扣减，不因时间自动过期、失效或清零；不增加有效期字段和过期提醒。食材可食用性由用户自行判断，保留备餐中的基本食品安全提示，不能将账面库存视为已验证安全的食品。

## 6. 替换必须真正修改食谱并重新验证

自动替换应优先在生成前或生成过程中完成，而不是在采购汇总后改名字。每个最终菜谱保存实际使用的食材 ID、重量、状态、变体步骤及必要的替换依据。

直接替换也要按正确数据源重算营养。条件替换需要考虑目标份量、能量、蛋白质、脂肪、碳水、纤维、钠、钙等；按餐及全周重新校验。无法保持合理餐次或菜谱质地、味道、工具与制作步骤时，选择其他完整菜谱而不是强行替换。

保留生熟换算、可食率、吸水率、出成率、商品密度的区别，避免重复计算。实际营养、配方和采购重量必须一致。数据未知则标记，不得当成零或编造数据。优先使用可信食物成分数据及商品标签，记录来源。

同步修改菜名（如必要）、食材用量、制作方法、营养数据、核心食材池、采购、分装、储存/复热建议、价格、库存扣减和历史快照。已取用、制作或完成的菜谱不允许自动改写，沿用 V2.3 已执行保护机制。

不重新引入主动操作时间、总耗时、等待时间的筛选、评分或硬约束。时间只作参考；烹饪可行性严格检查实际厨具，包括替换后所需的工具。烹饪复杂度如保留只能按非时间因素作为可选偏好。

## 7. 采购、价格与单位统一优化

继续严格按照用户指定购物次数执行，采购2次就是2个计划采购日，库存充足的批次可显示无需补购；备餐2＋2＋3仍为独立三个批次。食材替换、调味料补货、库存不足不得静默新增购物日。

采购清单按照主要食材、新鲜调味食材、常备调味料分别展示。默认突出待买项，库存已覆盖的项目放到“已有库存”折叠区；真实已购买记录仍可查看和修正，不能和“库存覆盖无需购买”混淆。

每项清晰显示实际商品名、建议采购数量、参考单价、预计补购金额及状态。将实际支付、剩余预计费用、预计总支出与食材消耗价值分开；保留广东参考价与用户自定义价格。替换前后比较同一计价口径下的实际补购成本，不以单价大小直接判断更便宜；包装取整、库存抵扣和可食率均正确计算。未知价格标记待补充，不按0元估算。

统一计量与包装：内部继续采用可靠的标准计量；液体油、醋、酱油等优先以瓶、毫升、升显示；固体可按克、斤、公斤；鸡蛋等计数商品可按个；包装名称应对应实际瓶、袋、盒、包，不能把所有包装统一显示成“包”。密度未知时不强行将克换算成毫升，允许按克显示并提供必要的自定义换算入口。保留实际购买单位、数量、净重及支付金额。实际确认购买和新增购买须分别记录，防止重复入库或覆盖历史。

例如已有橄榄油230g，可继续按原记录保留；若有可靠密度或包装标注则显示相应毫升。若本周兼容菜谱全部使用橄榄油且库存充足，则菜籽油不应进入待买清单。已有菜籽油记录仍保留，不能删除或改名。不能将既有库存抵扣显示成虚假的“已购一包”。

## 8. 集中备餐与实用份量

将同一批次中相同原材料及兼容工序合并，集中称重、煮饭、分装；不同做法、需要当天制作的食材保持独立安排。调味料只列本批预计用量及每餐实际配方，不要求分装油盐。

肉、蔬菜、主食可优先按实用的5g或10g增量优化；油、盐等按必要精度；鸡蛋优先自然份数并使用实际净重。取整发生在算法层，取整后重新校验营养与所有采购、分装、库存数据，而不是仅改变显示值。

替换后重新生成受影响的备餐批次与分装标签。只对尚未执行的任务调整；已买库存、实际支付、已取用记录不能被新计划覆盖。实际取用只扣一次。

## 9. 页面交互做减法

不新增主导航或独立替换规则管理页面。保持首页、食谱、采购、我的四项主导航。

在现有生成设置里默认启用“减少采购种类”，可以沿用现有采购集中度设置表达，不重复设置。高频流程保持：更新体重→沿用设置生成→采购→备餐。用户无需手动批准每个安全且符合既有偏好的等价替换。

食谱页显示最终真实食材及克数，必要时在详情提示“已优先使用家中橄榄油”。采购页顶部可简洁显示“本周使用 N 种 / 需买 M 种”，可折叠查看替换说明（原食材→实际食材、库存覆盖、是否新增采购）。不要伪造节省金额，只有用相同价格和约束基线计算后才能展示。

在尚未执行的菜谱详情复用现有“更换同类食材”入口，优先展示已有库存且规则允许的选项；替换后先重新校验。若需要增加采购种类、超预算或违反严格食材池，明确提示并由用户决定。禁止悄悄替换明确锁定的食材。减少确认弹窗、重复按钮、层层折叠；主分类与子项目层级分明。

## 10. 开发步骤

A. 检查最新主分支、已有 V2.3 进度、实际商品和菜谱分类；保存升级前基线及测试记录。

B. 扩展商品语义、替换规则及来源，建立独立测试，不改变现有营养 ID 与库存商品 ID 的含义。

C. 接入核心食材池、全周生成、换菜、换餐、换一天、保留食材重生成等所有入口。对库存、采购种类、包装和费用进行全周优化。

D. 接入备餐、采购、计量单位、价格和库存流水。保持已执行保护和向后兼容。

E. 最后精简 UI，执行真实浏览器及自动化验收，构建、提交、部署、更新 PWA 缓存。

## 11. 必须执行的测试

- 同一菜谱组涉及菜籽油、橄榄油时，指定适用橄榄油后可统一实际配方，另一种油不新增采购；实际库存分别保持，取用只扣橄榄油。
- 米醋替代适合的苹果醋菜谱后，菜谱、用量、价格及库存一致；不合理的酱料替换被拒绝。
- 验证肉类、鱼虾、鸡蛋、豆腐、奶类、主食、薯类、蔬菜、菌菇、水果、坚果、全部调料及其他采购分类的规则。各分类至少覆盖允许/条件/拒绝或无规则场景，不能只测油和醋。
- 鸡胸肉与熟鸡胸肉原料采购去重仍准确，真正购买即食成品则分别管理。
- 不会将牛奶与豆浆、鱼虾与豆腐等未经核验的不同商品等量互换。蛋白质、钙、钠、能量等变化正确重算；过敏原、忌口与锁定食材不能被绕过。
- 仅有蒸锅和煮锅时，替换后不会引入炒锅、烤箱等必需工具；耗时长的菜谱不因时间被排除。
- 库存充足时不重复采购，库存不足只补差额并正确计算包装。库存长期保留，不受日期失效影响；生成和替换不扣真实库存，实际取用只扣一次。
- 采购2次与备餐2＋2＋3独立执行，不因替换或补货额外增加采购日。
- 价格、实际支付、预计补购与总支出正确；液体单位与包装名称正确，密度未知时不编造；多次实际购买累计入库。
- 已取用、已制作或已完成的任务不能被优化覆盖；历史食谱、旧价格快照与库存购买流水保持不变。
- 用至少100个随机种子覆盖不同成年人虚构档案、三种采购模式、仅蒸煮、严格指定食材、有库存/无库存、有过敏及不同预算等。与升级前使用相同条件和种子对照，报告生成成功率、营养合格率、本周使用商品数、实际新增采购商品数、主要食材与调料种类数、库存利用量、预计费用、一次性使用食材数及运行时间。说明失败及不可比较样本，不能用降低营养标准换取数据改善。
- 测试360px、390px、430px手机宽度、浅深色、换菜后页面与费用更新、离线使用、数据迁移及PWA缓存升级。实际执行能够运行的测试，不能虚构结果。

## 12. 最终交付

提交代码前说明本次核验发现的根因、覆盖的食材分类、规则数量及未支持替换的原因；提供升级前后同一档案的食谱、实际采购清单和备餐对照，以及实际测试结果。若部分食材成分、密度或出成率没有可靠来源，明确说明并采用保守方案，不隐瞒。

完成修改后提交代码，通过项目现有 GitHub Actions 部署原正式网址，并验证发布状态和PWA版本；不能把未执行的部署或真机测试标成成功。保护现有个人档案、历史食谱、真实库存、购买流水及价格，禁止清空 IndexedDB。全程使用简体中文。

最终目标：相同原料不重复买，相似用途不必各买一种，所有品类优先复用库存，整周采购尽量少而合理，食谱真实可做、营养均衡、方便分装。
